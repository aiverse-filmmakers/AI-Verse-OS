# Build and verify learned skills

## Plan from the evidence

1. Review the whole source before drafting. Reconcile later decisions with earlier ideas and retain earlier failures as evidence for checks. If the member asks to see the plan first, show the proposed skills, their jobs and why each is needed, then wait at that point.
2. Inspect an authorized copy of the actual deliverable when learning how to reproduce it. Inspect representative states as well as the finished view when available. Record which interactions and design qualities worked. A screenshot or written account cannot verify interactions. If a referenced deliverable is inaccessible, say what that prevents you from learning.
3. For one repeatable job, prefer one skill. For a workflow made of independently reusable jobs, give the coordinating skill one job: own the overall deliverable and assemble the parts. Give each helper one job and explicit inputs, output shape, and verification. Put the matching conditions, call order, handoffs, and missing helper behavior in the coordinating skill. Resolve existing helpers before creating new ones. Call a helper explicitly when its inputs and conditions are met. Test the whole workflow plus each helper on its own.
4. Carry over decisions, not a project's inventory. Test sparse inputs and incremental updates. Where the evidence calls for a designed starter, make the starter ready to use with illustrative placeholders clearly marked. Add relevant sections when the project supplies material, route unfamiliar material without duplicating it, and put clarification questions where the member chose to answer them. If a method can work with or without an input, write both routes. Preserve any user decision about whether a reference may be used.
5. Use simple words people type when they need the outcome, including phrases that never mention the skill or artifact name. Write short numbered steps with concrete actions and checkpoints a smaller model can follow. Put long examples, templates, scripts, and starter assets in named files linked from the step that uses them. Test brief and ambiguous requests, and one nearby request that should choose a different skill. A trigger should cover relevant work without taking over unrelated tasks.

## Submit and activate

1. For a package whose only file is `SKILL.md`, use the normal `skills.learning-candidate` route. For a package with files, stage the complete candidate directory under the authorized source scope (inside `operator/` or the bound workspace). Inspect and test that exact directory. Do not convert runnable assets or essential references into appendices just to fit a text submission.
2. Use the Skills owner's complete package workflow for a directory. In hosts exposing `skills.library-import`, use the read only preview effect of that operation with `source_relative`, the appropriate visibility, and verified portability declarations for shared placement. Present the preview, its exact contents, and the approval needed before applying the returned plan. Apply only after approval and through the same authorized interface. If the host exposes only the text learning route, leave the complete directory staged for review and report the missing package route. Do not submit or activate an incomplete substitute.
3. Inspect existing proposals and active revisions. Identify exactly which new proposal or preview replaces which older one, with IDs and reasons. For an existing member package use the owner's revision workflow for its exact identity when available. Retire superseded proposals only after the replacement is verified and the member has authorized the retirement. For pending approval, give the exact IDs and the available owner approval action or ask for approval in plain language. Preserve the member's installed approval mode. Verify the owner's resulting state and read back the installed revision and its file inventory before saying it is active.
4. Save the complete package to the member library through its owner. After activation, check the OS response for `chat_listing`. A shared skill must have an exact active revision in both `.agents/skills/<name>/` (Codex) and `.claude/skills/<name>/` (Claude Code). If an approval ran directly in the Skills owner or listing is still pending, run `node scripts/sync-my-skills.mjs --json` in the OS project before reporting completion. Verify the active revision in the resolver and compare both startup copies, including referenced files. If another skill already owns the name, resolve the name before calling it ready. Keep workspace only packages in their workspace and use scoped discovery for those.
5. In a fresh authorized chat for each supported host, try a plain request without naming the skills or loading them first. Verify the coordinating skill was selected, the helpers ran only where needed, and the result passes an observable check. Compare with a request that should leave those skills unused. Check that implicit invocation is allowed for those hosts and use a specific short description with common starting phrases and clear limits. Mark proposal, activation, listing, native discovery, and successful invocation separately. If a fresh chat cannot be tested, state which behaviors are verified. Finding a skill in a startup folder proves the copy exists.

## Interactive deliverables across apps

For an interactive board or similar output, keep the editable source and assets in the project. Include a portable browser version where the interaction can be implemented as a web app. Record each host's supported viewing route in the learned skill. Use a Claude Artifact only when that feature is available and publishing the project material is authorized. In Codex use a local HTML preview or open a local project web app in the browser. Support a regular browser for terminal sessions or unavailable previews. Keep host specific publishing separate from building the deliverable.

If the workflow depends on a canvas that can be panned and zoomed, model it as an interaction the app implements. Verify pan, zoom, fit to content, and adding an item beyond the initial view. Verify any 3D viewer or other essential interaction separately. Record the working host and any performance or rendering limits found. An HTML file or a static screenshot alone does not prove that an interaction works.
