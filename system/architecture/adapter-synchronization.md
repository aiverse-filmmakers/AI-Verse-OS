# Runtime Adapter Synchronization

AI-Verse OS keeps one editable source for built-in capabilities: `system/capabilities/`.

Runtime-specific materializations are generated peers:

- Claude: `.claude/skills/`
- Codex: `.agents/skills/`

Neither runtime tree is the editable source of the other.

## Ownership ledger

`scripts/sync-runtime-adapters.mjs` records OS-owned generated files in `runtime/adapters/os-owned.json`. Runtime state is gitignored and rebuildable.

Each owned file record binds:

- the target runtime path
- the canonical source path
- the SHA-256 digest of the last bytes generated by the OS

The ledger is an ownership record, not a permission grant and not package truth.

## Safe replacement rule

For a canonical OS file, synchronization may write a runtime target when:

1. the target does not exist, or
2. the target exists, is not yet owned, and its bytes already equal the canonical source, or
3. the target is recorded as OS-owned and its current digest still equals the last generated digest.

If an owned target was locally modified after generation, synchronization preserves it and reports a conflict. If an unowned target differs from the canonical file, it is also preserved and reported as a conflict.

Unknown files and unknown capability directories are never removed merely because they do not exist in `system/capabilities/`. This includes optional extension adapters such as AI-Verse Memory and user-created runtime adapters.

When a canonical OS source is removed, a previously owned target is deleted only if its digest still matches the last generated digest. A modified target is preserved and ownership is released.

## Path safety

The synchronizer refuses to modify paths that escape the OS root or pass through symbolic links. Canonical capability sources must not contain symbolic links. Ownership state that is malformed or from an unsupported schema fails closed rather than causing guessed ownership.

## Commands

Synchronize every built-in capability:

```bash
node scripts/sync-runtime-adapters.mjs
```

The historical command remains a compatibility entrypoint and now performs the same peer generation:

```bash
bash scripts/sync-codex-skills.sh
```

Synchronize one capability:

```bash
bash scripts/sync-codex-skills.sh onboard
```

A conflict exits with status `2`. No conflicting or unowned file is overwritten. Resolve the local difference deliberately, then run synchronization again.

## Extension boundary

Extensions own their own adapter files and register through `.aiverse/extensions/registry.json`. OS synchronization must not adopt or rewrite extension files unless they are byte-identical to an OS canonical capability path being initialized, in which case that exact target file becomes OS-owned.

This adapter ownership model is independent of future capability-provider discovery and Skills generation lifecycles. Those layers may add generation identity later, but they must preserve the same no-silent-overwrite rule.
